## ۱. ادمین کیست (دقیقاً همان‌طور که پیاده است)

هر آپدیت ادمین است اگر **یا** (`src/admin.ts:28-36`):

۱. `env.ADMIN_CHAT_ID` (در `wrangler.jsonc → vars`) برابر رشتهٔ شناسهٔ عددی
   بازیگر باشد (trim شده؛ **تک id**، نه لیست ویرگولی)، **یا**
۲. سطر `customers` بازیگر `is_admin = 1` داشته باشد.

یک‌بار در هر آپدیت محاسبه می‌شود (`ctx.isAdmin`) و در تک‌تک هندلرها و شاخه‌های
callback ادمین (`adm:`, `tsk:`, `prc:`, `sal:`) **دوباره سمت سرور** چک می‌شود —
تپِ جعلی/بیگانهٔ مشتری = توست خنثی و صفر اثر.

**افزودن ادمین دوم:** یک‌بار `/start` بزند (تا سطرش ساخته شود)، سپس:

```bash
npx wrangler d1 execute telbot-db --remote --command \
  "UPDATE customers SET is_admin=1 WHERE telegram_user_id='<شناسه عددی>';"
```

**حذف:** `is_admin=0`. (تغییر `ADMIN_CHAT_ID` نیازمند ویرایش vars + redeploy است.)

## ۲. مرجع فرمان‌ها (فقط فرمان‌های واقعیِ موجود)

| فرمان | چه‌کسی | کارکرد |
| --- | --- | --- |
| `/pending` | ادمین | ۱۰ سفارش آخر `awaiting_review` با ✅/❌ هر ردیف؛ فیش‌های رسیده push با همان دکمه‌ها. |
| `/failed` | ادمین | ۱۰ `failed` آخر با دکمهٔ `🔁 <id>…`؛ retry از حالت failed و زیر سقف `max_attempts` ادعا می‌کند. |
| `/tickets` | ادمین | تا ۱۰ تیکت زنده؛ هر ردیف: 💬 پاسخ / 👁 جزئیات / ✅ بستن؛ پیام تازهٔ مشتری push با 💬. |
| `/announce [متن]` | ادمین | بادی draft → preview → 📢 ارسال → fan-out چانکی + «ادامه ارسال ➡️»؛ `/announcements` وضعیت ۵ کارِ اخیر. |
| `/credit <id تلگرام> [مبلغ]` | ادمین | اعطای اعتبار: usage اگر آبج نبود؛ arm ← تایپ مبلغ ← اعمال مراقبت‌شده/سقف‌دار + جفت دفتر کل. |
| `/debit <id تلگرام> [مبلغ]` | ادمین | کسر اعتبار، همان مسیر (منفی‌شدن ناممکن). |
| `/pricing` | ادمین | نمای سند زنده → field → arm (۱۵دقیقه) → تایپ → ✅ → CAS + `settings_audit`. [جزئیات](pricing.md). |
| `/sales` | ادمین | وضعیت + 🛑 توقف سرویس / 🟢 فعال‌سازی سرویس / 🔄 نمایش دوباره؛ CAS + audit. [جزئیات](pricing.md). |
| `/start` `/help` `/cancel` | همه | UX مشتری. |

فرمان ناشناخته → پیام «ناشناس» + منوی اصلی.

## ۳. گردش‌های کاری روزانه

### بررسی فیش

۱. فیش (عکس/سند + خلاصه: id، قیمت نهایی، مشخصات سرویس؛ سفارش تمدید با
   برچسب و id سرویس روشن است).
۲. صحت را در **فاصل بانکی خودتان** چک کنید — ربات به حساب شما دسترسی ندارد و
   تصویر سند می‌تواند جعلی باشد.
۳. ✅ ← approved ← پروژن ظرف چند ثانیه (یا اطلاع «در دست بررسی است» +
   `/failed` در شکست). ❌ ← دلیل (≤۲۰۰ کاراکتر یا دکمهٔ skip) ← اطلاع مشتری +
   **برگشت خودکار اعتبار کیف‌پول** (برندهٔ same-batch).
۴. تپ دوباره/ادمین موازی: خنثی (گذار مراقبت‌شده).

### نجات پروژن ناموفق

`/failed` → 🔁 (سقف تلاش). تکرار شکست یعنی: پنل down، سند `provisioning`
خراب/disabled، نبود کلید/URL، یا `group_ids` نامعتبر — دلیل sanitize‌شدهٔ
کوتاه + `/health` + `tail` ([عیب‌یابی](troubleshooting.md)).
سرویس/سفارش سالم می‌ماند؛ adoption از ساخت تکراری جلوگیری می‌کند.

⚠️ **نکتهٔ واقعیِ عملیات:** چون skip‌های پیکربندی **پیش از ادعا** رخ می‌دهند،
سفارشی که بی‌کلید در `approved` مانده، هیچ صف/Retry UI ندارد (`/failed` فقط
`failed` را نشان می‌دهد). درمان: پیکربندی را درست کنید، سپس با یک UPDATE
مستند به `awaiting_review` برگردانید تا ✅ عادی (ادعا+audit خودش) اجرا شود —
راه‌حل دقیق در [عیب‌یابی §E](troubleshooting.md).

### پاسخ تیکت

`/tickets` → 💬 (یا روی push) → تایپ پاسخ (sanitize ≤۲۰۰۰) → relay به مشتری؛
تیکت `answered`؛ پاسخ مشتری دوباره `open` و push؛ ✅ بستن.

### اطلاعیه

`/announce متن` ← تأیید draft ← چانک‌ها تا پایان؛ قطع‌شده با
`/announcements`/دکمهٔ ادامه از سر گرفته می‌شود. متن عیناً برای هر دو زبان
رندر می‌شود → دوزبانه بنویسید اگر مخاطب مخلوط است.

### توقف فروش برای نگهداری

`/sales` → 🛑؛ بعد 🟢؛ می‌توانید `/announce` ازسرگیری بفرستید. سفارش‌های معوق
قبلی قابل‌تأیید می‌مانند (پول سرگردان نمی‌ماند).

### اصلاح قیمت (زنده، بدون redeploy)

`/pricing` → فیلد ← عدد exact (تومان) ← ✅. پیغام رقابت؟ ادمین دیگر برنده
شده — دوباره view و تکرار intent. ممیزی: rows `settings_audit`.

## ۴. ویرایش‌های مستقیم D1 (فاقد UI)

نردبان‌های حجم/مدت، `payment_info`، `provisioning`، `renewal`، `wallet`،
`referral` — نمونه SQL در [پیکربندی](configuration.md).
همیشه قبل/بعد را ببینید، تک UPDATE، `"schema"` درست، و یادِ
fail-closed-شدنِ کاتالوگ به‌خاطر نقص پوشش قیمت باشید؛ پس‌از ویرایش smoke بزنید.

## ۵. یادآوری‌های ایمنی عملیات

- توکن/secret وب‌هوک/کلید پنل/کارت را به هیچ‌کس ندهید؛ ادمین = **مجموعهٔ
  شناسه‌هاست**، نه رمز عبور.
- digest 8C همان مسیر کد بررسی است — امنیت تأیید از digest با `/pending`Equal.
- `settings_audit` و `order_events` فقط-افزودنی‌اند؛ تصمیم از تاریخچه پاک
  نمی‌شود (عمداً).
- پرامپت‌های متن‌آزاد (دلیل رد، پاسخ، مبلغ) پس از ۱۵ دقیقه منقضی و تازه
  می‌شوند — اثر جانبی ندارند.
- در توقف فروش، تأیید سفارش قبلی + پروژن‌شان عمداً آزاد است؛ خودِ ادمین‌ها
  همیشه در دسترس‌اند.
