## ۱. مدیریت secret‌ها

| Secret | مسیر | هرگز ظاهر نمی‌شود در |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | HTTPS خروجی به api.telegram.org | کد، git، لاگ، D1، پیام تلگرام |
| `TELEGRAM_WEBHOOK_SECRET` | فقط بررسی هدر ورودی | لاگ، پیام، مستندات |
| `PASARGUARD_API_KEY` | هدر `x-api-key` HTTPS | لاگ، متن تلگرام، D1 |
| `PAYMENT_CARD_NUMBER` | فقط حبابِ دستور واریز | فیلد D1 (لودر نادیده می‌گیرد)، لاگ (جز نامِ رویدادِ پیکربندی‌نشدگی) |

`.dev.vars` در .gitignore؛ در پروداکشن Worker secret. چرخش = `secret put`
جدیده + `setWebhook` مجدد/پروپاگیشن؛ کلید پنل در UI پنل rotate می‌شود.

## ۲. احراز ورودی وب‌هوک (fail-closed)

`src/routes/webhook.ts`: secret تنظیم‌نشده ⇒ **503** بدون پردازش؛ هدر
ناقص/غلط ⇒ **401** با `timingSafeEqual` (XOR انباشتهٔ زمان‌ثابت،
`security.ts:28-38` — تنها نشتی طول رشته است)؛ JSON خراب ⇒ 400؛ بعد از احراز
**همیشه 200 ACK** تا retry-storm تلگرام ایجاد نشود (خطا لاگ می‌شود). تنها
مسیرهای عمومی `/health` (فقط بولین‌های presence) و وب‌هوک هستند؛ بقیه 404.

## ۳. اعتبارسنجی ورودی (callback = دادهٔ دشمن)

- الگوی عمومی `^[a-z]{2,6}:[a-z0-9][a-z0-9_]{0,23}$` + allowlist namespaces
  ثابت (`menu:*`, `act:*`, `step:*`, `ord:confirm`, `cfg:auto`, `wlt:*`,
  `gud:*`, `lang:fa|en`).
- namespaceهایِ دارای id پارسر مستقل و سخت‌گیر: `adm:(ok|no|skip|rt):`, `svc:(det|ref|rnw):`,
  `tsk:(rp|cl|vw):`, `ann:(go|ct):` — دقیقاً ULID ۲۸‌کاراکتهٔ minted (Crockford
  base32).
- گرامر `prc:` و `sal:` جدا (`prc:e_<token>`/`prc:menu|ok|no`؛
  `sal:view|stop|start`); هیچ چیز دیگر route نمی‌شود.
- مدیا: `file_id` با `/^[A-Za-z0-9_-]{1,255}$/`؛ از عکس بزرگ‌ترین رندرانت
  برداشته می‌شود؛ خراب ⇒ null (id forged/over-sized به DB نمی‌رسد).
- متن‌آزاد sanitize سقف‌دار: نام کانفیگ ≤۶۴ و بدون `/` شروع، مرجع پرداخت
  ≤۱۲۸، دلیل رد ≤۲۰۰، بدنهٔ تیکت/اطلاعیه ≤۲۰۰۰، کنترل‌کاراکتر حذف؛ ارقام
  فارسی/عربی normalize، سقف ۸ رقم (و ۱۲/۱۳ برای مبالغِ با علامتِ عمداً مجاز
  کیف‌پول)؛ منفی هیچ‌وقت در قیمت پارس نمی‌شود.
- مقداریِ دکمه‌ها (`vol:30`…) هر بار با **کاتالوگ تازه** تطبیق — دکمه راهنما
  است، نه حقیقت. `config_name` فقط نمایشی است و مسیر به پنل ندارد.
- ساختاری: SQL فقط prepared + `.bind()`؛ رندر HTML فقط جایی که لازم و با escape
  کامل (`format.ts`)؛ اسناد D1 با CHECK `json_valid`؛ JSON‌خوانی تدافعی.

## ۴. مجوزها (Authorization)

- ادمین: `ADMIN_CHAT_ID` **یا** `customers.is_admin`؛ محاسبهٔ یک‌باره +
  **بازرسی دوباره در همهٔ شاخه‌ها/بک‌کول‌های** `adm:`/`tsk:`/`prc:`/`sal:` —
  غیرادمین حتی با payload معتبر خنثی می‌شود.
- اکشن‌های `svc:*` مالکیت را داخل WHERE ادعا می‌کنند؛ id بیگانه صفر نشتی.
- هیچ سلسله‌مراتب RBAC وجود ندارد؛ سطح دسترسی «ادمین» بولی است. جریانِ اختیارِ تازه اختراع نکنید.
-بازگشت وجه/پاداش/پروژن فقط در پشتِ برندهٔ ادعای ادمین یا مسیر سیستمی اجرا می‌شوند؛
  هیچ‌کدام از کیبورد مشتری قابل فراخوانی نیست.

## ۵. تمامیت حالت و همزمانی (CAS، ادعا، idempotency)

- گذارهای سفارش: تک UPDATE با `state=` در WHERE + بررسی affected-rows؛
  فقط برنده notify/provision/refund می‌کند — دابل‌تپ/دوادمین همگرا به یک اثر.
- ادعای پروژن سقف تلاش را در خودِ UPDATE دارد؛ UNIQUE username/user_id +
  ادعای name پیش از نوشتن، سرویس تکراری را غیرممکن می‌کند؛ هدف تمدید **مطلق**
  پیش از PUT ادعا و بعد verify می‌شود (adopt اگر پنل جلو زده باشد).
- سفارش: توکن سشن ← ایندکس یکتای جزئی `idempotency_key` ← re-read برندهٔ race.
  پرداخت کیف‌پول: NOT EXISTS + يكتایِ `order_payment`؛ refundها هم سطر
  `order_refund` را ادعا می‌کنند و حتی creditِ باخته را re-apply (نه double، نه
  lost).
- replay تلگرام با `update_dedupe` قبل از هر کاری خنثی. یادآور/اعلان: ادعای
  مرحله‌ای/lease با PK/یکتاییِ ساختاری (at-most-once؛ نشتی فقط «یک بار دیرتر»
  خودترمیم).
- پرامپت‌های ادمین: یکی‌به‌ازای هر ادمین، TTL ۱۵ دقیقه؛ مقدار پولی staging
  سمت سرور (داخل payload دکمه هیچ‌وقت).

## ۶. ایمنی پول

عددصحیح مطلق با رد سرریز (`Number.isSafeInteger` + سقف تا ۱۰¹²)؛ UPDATE موجودی
مراقبت‌شده در برابر منفی + سقف؛ `balance_after` بازخوان‌شده از سطر؛ snapshot
مبلغِ سفارش تغییرناپذیر؛ **هیچ مسیر کدی به پرداختِ unverified اعتماد نمی‌کند**
(دستیِ ادمین تنها گذر)؛ گیت‌های کیف‌پول سخت **پیش از** برداشت.

## ۷. ماتریس fail-open / fail-closed (رفتار دقیقاً فعلی)

| تنظیم/مشکل | رفتار | استدلال |
| --- | --- | --- |
| نبود `TELEGRAM_WEBHOOK_SECRET` | **closed** (503) | آپدیت بی‌احراز پرمعنا نیست |
| نبود `PAYMENT_CARD_NUMBER` | **closed** (نمایش «در دسترس نیست») | هرگز کارت اشتباه/پیش‌فرض نشان نده |
| کاتالوگ/قیمت خراب یا حفرهٔ پوشش | **closed** («موقتاً در دسترس نیست») | زیر ladderِ خراب فروش نرو |
| `provisioning` مفقود/خراب/disabled یا نبود کلید/URL | **closed no-op** (سفارش جابه‌جا نمی‌شود) | تماس نصفه‌نیمه با پنل ممنوع |
| سند `renewal`/`wallet`/`referral` خراب | **closed برای همان قابلیت** | کلیدهای پولی |
| سند `sales` مفقود/خراب/خطای DB | **OPEN (فروش مجاز)** | خلل تنظیماتی نباید کسب‌وکار را بخواباند؛ فقط `stopped:true` صریح |
| خطای خوانش پنل در سرویس‌ها/جاروب‌ها | تنزل به snapshot محلی | نمایشی؛ تصمیم پولی نیست |
| خطای DB فهرست ادمین | تنزل به `ADMIN_CHAT_ID` | فوروارد نباید بمیرد |

## ۸. ملاحظات وب‌هوک/تلگرام

- یک وب‌هوک با `secret_token` standard؛ چرخش: [telegram](telegram.md).
  Worker session ندارد؛ همه‌چیز D1.
- شکست send (بلاک 403 و…) اعتبارِ ادعاها را نمی‌شکند: `sent` تنها با تأیید
  تلگرام نوشته می‌شود (اعلان‌ها)؛ سایر مسیرها null-tolerant‌اند.
- `/health` تنها دادهٔ عمومی: booleans. no secrets exposure.
- لاگ: فقط event-name‌ها/`error=${name}`؛ مقدار راز و بدنهٔ خام پنل (≤۲۰۰
  کاراکتر sanitize‌شده) وارد رشتهٔ لاگ نمی‌شود.

## ۹. مرزهایی که محافظت نمی‌شوند (بایست بدانید)

- دارندهٔ توکن ربات / اکانت Cloudflare / دسترسی ادمینِ پنل = صاحب نظام (trust
  پلتفرم).
- کیفیت تأیید فیش = قضاوت انسانی ادمین؛ جعلِ تصویر فقط با صورت‌حساب بانکی
  گرفته می‌شود.
- متن‌های ادمین‌نویس (اطلاعیه/دستور واریز/پاسخ تیکت) عیناً رندر می‌شوند؛
  حساب ادمین نقش مورد‌اعتماد است.
- rate-limit افزون بر خود تلگرام و update-dedupe نیست؛ ضداسپمِ بارگذاری مکرر
  فیش فراتر از قانون «جایگزینی + audit» state نیست (همان پیاده شده).
